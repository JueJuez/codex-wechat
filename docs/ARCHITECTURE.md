# 架构与接入边界

当前方案使用 Codex 官方 app-server 的本机 stdio JSONL 协议，复用已安装 Codex 的登录、模型与本机工具配置。
这是主动驱动 Codex 的会话客户端，MCP 单独提供工具不能承担微信入站后创建任务的宿主职责。
官方接口说明：https://learn.chatgpt.com/docs/app-server。

- `vendor/wechat-core`：上游 iLink 登录、长轮询、文本、加密附件传输。
- `src/codex.mjs`：子进程、请求匹配、通知与服务器交互请求分发。
- `src/bridge.mjs`：绑定用户检查、持久化入站任务、会话映射、排队、审批与结果回传。
- `src/storage.mjs`：严格加载状态、原子顺序写入、单进程锁。
- `src/cli.mjs`：配置、扫码、凭据与通道生命周期。
- `run.ps1`：Windows 可直接执行的启动入口及构建检查。

模型回合不阻塞微信入站轮询；审批和取消命令直接处理，所以执行中的任务仍能收到手机回复。
本版全局一次执行一个任务，避免共享工作区同时修改冲突。
输出按回复上限分段，按发送顺序串行发往微信；没有逐 token 请求，避免大量发送。
取消支持正在执行的 turn、准备附件阶段，以及排队消息。

命令执行审批显示请求的命令和工作目录；文件修改审批附带已收到的变更路径和 diff。
用户回答工具支持问题ID逐一回答。不支持的其他服务器交互请求明确拒绝并提示，不能静默批准。

上游微信轮询原本先提交游标再调用宿主，无法保证本桥接持久化入站队列。
本地补丁改为所有消息成功入队后提交游标，失败时保留旧游标并退避；对应确定性测试覆盖顺序及磁盘失败。

本机版本 schema 与在线文档可能有差异。当前验证过的线程 sandbox 参数使用
`workspace-write` / `danger-full-access`；不要直接套用 turn 层 sandboxPolicy 的 camelCase type。
兼容性验证入口为 `doctor`（握手与登录）和 `smoke`（真实新建会话及命令执行）。

可后续扩展：自动文件发送工具、后台服务、已有桌面会话选择、更多交互请求与语音处理。
这些不是当前已实现能力。

已立项：多后端跨平台路由（单桥接进程内挂多个 agent 适配器，`@前缀` 路由、回传带平台标识、
每后端独立队列并行）。设计与本机可行性实测见 [02-plan/multi-backend-plan.md](02-plan/multi-backend-plan.md)。
当前代码仍是单 Codex 后端，微信单轮询约束是采用单桥多后端形态的决定性原因。
